Shannon Entropy
// H = Σ −pᵢ log₂ pᵢ — minimum average bits per symbol
▶ Concept & Method show
What is entropy?
Entropy H is the theoretical minimum average number of bits per symbol any compression scheme could ever achieve for a given set of frequencies. It is a lower bound — you cannot do better, no matter how clever your code is. Huffman coding gets within 1 bit of this bound.
The intuition
A symbol that appears half the time (p = 0.5) carries 1 bit of information. One that appears a quarter of the time (p = 0.25) carries 2 bits. In general, a symbol with probability p carries −log₂(p) bits. Entropy is the weighted average of this over all symbols.
Step-by-step method
1Find total N = sum of all frequencies.
2For each symbol i: compute pᵢ = freqᵢ / N
3For each symbol i: compute −pᵢ log₂(pᵢ)
4H = sum of all −pᵢ log₂(pᵢ) values
5Total minimum bits = N × H
Exam shortcut — avoid fractions
Instead of computing each pᵢ = f/N then taking log₂(f/N), use:

N·H = N·log₂N − Σ fᵢ·log₂fᵢ

This takes log of whole numbers (5, 2, 11...) instead of fractions (5/11...) — same result, less painful.

Compute N·H first, then divide by N to get H.

▶ On a standard calculator (no log₂ button):

N·H = (N·log(N) − Σ fᵢ·log(fᵢ)) / log(2)

Since every term needs dividing by log(2), factor it out and do one division at the very end. log(2) = 0.3010 — write this on your cheat sheet.

Steps: (1) compute N·log(N), (2) compute each fᵢ·log(fᵢ) and sum, (3) subtract, (4) divide by 0.3010, (5) divide by N.
Worked example — A=5, B=2, C=2, D=1, E=1
N = 11
11H = −(5·log₂(5/11) + 2·log₂(2/11) + 2·log₂(2/11) + 1·log₂(1/11) + 1·log₂(1/11))
= −(5·(−1.137) + 2·(−2.459) + 2·(−2.459) + 1·(−3.459) + 1·(−3.459))
= 5.686 + 4.918 + 4.918 + 3.459 + 3.459 = 22.44
H = 22.44 / 11 ≈ 2.04 bits/symbol
Common exam traps
⚠ H is bits per symbol, not total bits — always multiply by N for the total.
⚠ log₂(x) = ln(x)/ln(2) on a calculator.
⚠ The answer is always between 0 (only one symbol) and log₂(n) (all symbols equally likely).

Rabin-Karp Hashing
// compute p, h, t₀, and rolling hash values step by step
▶ Concept & Method show
What is Rabin-Karp?
Rabin-Karp is a string-matching algorithm that uses hashing to find a pattern P inside a text T. Instead of comparing characters one by one at every position, it computes a hash of the pattern and a rolling hash of each window of T. Only when the hashes match does it do a character-by-character verification. This makes the average case O(n + m).
Symbol glossary
T — the text being searched (length n)
P — the pattern to find (length m)
n — length of T
m — length of P
d — radix (base). Use 10 for digit strings, 26 or 256 for letters
q — a prime modulus to keep hash values small and avoid overflow
h — precomputed multiplier: d^(m−1) mod q. Represents the positional weight of the leftmost character in a window
p — hash of the pattern P
t₀ — hash of the first window of T (characters T[1..m])
tₛ — hash of the window starting at position s. A hash match (tₛ = p) means a candidate match — needs verification
spurious hit — when tₛ = p but the actual characters don't match P. These are false positives caused by hash collisions modulo q
Step-by-step algorithm
1Compute h = d^(m−1) mod q. Multiply 1 by d a total of (m−1) times, taking mod q each time.
2Compute p using Horner's rule on P: start with 0, then for each character c in P left to right: p = (p · d + c) mod q
3Compute t₀ using Horner's rule on T[1..m]: same formula as above but on the first m characters of T.
4Compare t₀ with p. If equal, verify T[1..m] = P character by character.
5Slide the window: for each s from 1 to n−m, compute tₛ = (d · (tₛ₋₁ − T[s] · h) + T[s+m]) mod q. Add q if negative.
6Compare each tₛ with p. On a hash match, verify the actual characters. A mismatch after equal hashes is a spurious hit.
Worked example — T=31415, P=26, d=10, q=11
m = 2, n = 5

h = 10^(2−1) mod 11 = 10 mod 11 = 10

p (Horner on "26"): 0→(0·10+2)=2→(2·10+6)=26 mod 11 = 4

t₀ (Horner on "31"): 0→(0·10+3)=3→(3·10+1)=31 mod 11 = 9

t₁: (10·(9 − 3·10) + 4) mod 11 = (10·(9−30)+4) mod 11 = (10·(−21)+4) mod 11 = (−206) mod 11 = 2 (add multiples of 11 until positive)

t₂: (10·(2 − 1·10) + 4) mod 11 = (10·(−8)+4) mod 11 = −76 mod 11 = 0

t₃: (10·(0 − 4·10) + 1) mod 11 = (10·(−40)+1) mod 11 = −399 mod 11 = 7

p = 4. Compare: t₀=9 ✗, t₁=2 ✗, t₂=0 ✗, t₃=7 ✗ → no match found.
The rolling hash intuition
Think of the window hash as a base-d number mod q. When you slide right by one position, you remove the leftmost digit (multiply it by h to get its positional value, then subtract), shift everything left (multiply by d), and add the new rightmost digit. This is why you precompute h — it's the weight of the leftmost character's position.
Complexity & exam notes
⚠ Average case: O(n + m) — few spurious hits with a good prime q
⚠ Worst case: O(nm) — if every window is a spurious hit (e.g. all same character, q=2)
⚠ Always add q if the rolling hash goes negative before taking mod
⚠ q should be prime and large enough that spurious hits are rare — but small enough for easy arithmetic
⚠ A spurious hit costs O(m) to verify, so minimising them is key
